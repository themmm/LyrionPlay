**What the current code does with a 3-second answer.** I read `app/Sources/PlayerCore/LMS.swift` to check that the earlier fixes are still in place:

- **No timeout.** The request has a 4 s limit (`LMS.swift:225`), so a 3 s reply is accepted.
- **A changed setting is safe.** If the server setting changed while the check was running, `ServerChoice.checked(setting:…)` (`LMS.swift:44-49`) throws the result away. The old server can't come back, and its player states aren't kept. The agent then checks the new server straight away.
- **The slow answer is logged once.** The reply is over `slowAnswer` (2 s), so agent.log gets one "LMS check of … took 3.0 s" line. When answers are fast again it gets "back under 2 s … after K slower, the slowest M s" (`LMSCheckLog.timed`, `LMS.swift:118-137`). These lines are how a real stall would be spotted.
- **Already tested.** `ServerChoosing` and `ServerCheckLogging` test these paths, and the setting-change race was checked against a stand-in LMS (§B, 2026-10-11 09:00 UTC).
