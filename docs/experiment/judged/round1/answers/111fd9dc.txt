**Things I checked that are fine:**
- **The 6-byte request:** `sizeof(request)` sends `"eUUID\0"`. The trailing NUL is the TLV's length byte (0), which is what LMS's TLV parser expects. The test at `:923` checks exactly these 6 bytes.
- **The timeout:** the 250 ms wait is not a strict total. It starts again after each reply that gets dropped. The only reply that can be dropped is one from another address of the same server, and that adds a round trip at most. This is part of the declined residual, not something new.
- **The source port:** it isn't checked. The socket is new on every connect and uses a random local port, so only the server it asked replies to it. A stale reply can't carry over from an earlier connect.
- **A reply that doesn't parse:** a reply from the right address with no usable UUID ends that try, and the second try runs. A late answer to the first request, arriving during the second try, is still from the same server, so it's correct to accept it.
- **`parse_server_uuid`:** its bounds checks are correct (`i + 5 + n > len`, `n <= SERVER_UUID_LEN`, all characters printable), and a UUID that is too long is skipped, not copied.
- **Byte order:** addresses are compared in network order on both sides, and the port is `htons`-converted. LMS on the same Mac (127.0.0.1 or its own LAN address) and LMS in Docker with UDP 3483 mapped both answer from the address that was asked.
- **Interrupted wait:** a signal during `poll` only ends the current wait early. At worst it costs one more 250 ms try at shutdown.
