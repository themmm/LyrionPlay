## Findings

**1. Low (hardening): `process_setd` assumes the incoming name ends with a NUL byte inside the packet** — `engine/slimproto.c:737`, `:742`, `:744`

- **The cause:** `slimproto_run` passes `process()` its static 4 KB receive buffer (`:828`, `:859`). Nothing ends the packet with a NUL, and leftover bytes from earlier, longer packets stay in the buffer. `strncpy` at `:737` stops after 64 bytes, but `LOG_INFO("set name: %s", setd->data)` (`:742`) and the confirmation `sendSETDName(setd->data)` (`:744`, which calls `strlen`) read until they find a NUL.
- **What goes wrong:** if a `setd` name ever arrives without its NUL, the player name picks up stale bytes, up to 63 of them.
  - That name is cut to whole characters, written to the `-N` file with `F_FULLFSYNC`, and the server is added to the server list.
  - The confirmation sends the longer, corrupted text back to LMS. LMS sees a value different from its own and takes it as a rename. Both sides then keep the corrupted name.
  - If the packet fills all 4096 bytes, `strlen` can run past the end of the array.
- **Why it's low:** upstream squeezelite has the same code. As far as I know, LMS 9.1 always ends the name with a NUL. I did not check this against the LMS source in this session. Before LyrionPlay, a bad name stayed in memory; now it is written to disk and sent back to LMS.
- **Fix:** take the name from at most `len - 5` bytes (`memchr` for the NUL, or copy into a terminated local buffer). Then use that copy for the log, the confirmation and `player_name`.
